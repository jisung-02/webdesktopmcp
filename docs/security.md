# webdesktopmcp 보안 모델

W3C WebMCP 드래프트의 위협 모델(§6)을 데스크톱 환경에 맞게 적용한 것입니다. 에이전트는 ①사용자의 로그인 세션(웹뷰 쿠키)을 상속하고, ②앱의 개인화 데이터에 접근하며, ③여러 도구의 출력을 결합할 수 있다는 점을 전제합니다.

## 구조적 방어 (라이브러리가 강제)

| 방어 | 내용 |
|---|---|
| 루프백 전용 바인딩 | 로컬 MCP 서버는 `127.0.0.1`만 바인딩. 외부 인터페이스 노출 없음. |
| Bearer 토큰 | 모든 MCP 요청에 토큰 필수. 토큰은 프로세스 시작 시 `crypto.randomBytes`로 생성. 상수시간 비교. |
| 레지스트리 파일 권한 | `~/.webdesktopmcp/registry.json`은 mode 0600, 원자적 쓰기(tmp+rename). |
| pid 생존 확인 | CLI 셈은 죽은 프로세스의 스태일 엔트리를 무시. |
| 도구 이름 전역 유니크 | 프레임 간 도구 셰도잉(사용자 혼동·공격) 방지 — 중복 등록은 거부. |
| `exposedTo` 프라이버시 필터 | `exposedTo`가 지정된 도구는 외부 MCP 클라이언트의 `tools/list`에서 숨겨질 뿐 아니라 **`tools/call`로 이름 직접 호출도 게이트에서 거부**된다(인페이지 에이전트 전용). 과잉 파라미터화를 통한 핑거프린팅 완화. |
| 실행은 가시 웹뷰에서 | 스펙과 동일 — 헤드리스 실행 없음. 사용자가 화면에서 도구 동작을 볼 수 있음. |
| 확인 훅 | `confirmToolCall`(Electron) / `SetConfirmHook`(Go)로 민감 도구 호출 전 네이티브 동의 절차 삽입 가능. 데모 앱은 읽기 전용 도구만 자동 통과시킴. |
| 취소 전파 | MCP 클라이언트의 취소가 AbortSignal로 웹뷰 execute 콜백까지 전파. |

## 남는 위험 (사용자/앱 개발자가 관리)

스펙이 명시하는 프롬프트 인젝션 계열은 프로토콜이 아니라 **에이전트와 앱 개발자 측** 방어 과제입니다:

1. **Tool poisoning** — 도구 name/description은 에이전트의 지시로 읽힙니다. 앱 개발자는 설명에 행동 지시를 섞지 말아야 하고, 에이전트는 도구 메타데이터를 신뢰 지시로 취급하면 안 됩니다.
2. **Output injection** — 도구 반환값(특히 UGC가 포함된)에 에이전트를 조종하는 지시가 숨을 수 있습니다. `annotations.untrustedContentHint`를 선언하고, 에이전트 측은 도구 출력을 spotlighting/살균 처리해야 합니다.
3. **의도 왜곡** — `finalizeCart`("카트 확정")가 실제로는 결제를 트리거하는 식의 설명-동작 불일치. 앱 개발자는 설명을 실제 부작용과 일치시키고, 부작용 있는 도구에는 `readOnlyHint: false`를 명시해야 합니다. 에이전트 측 확인 다이얼로그(`confirmToolCall`)를 권장합니다.
4. **과잉 파라미터화** — 개인화 값을 파라미터로 받는 도구는 사이트에 프로파일링 데이터를 흘려보낼 수 있습니다. 필요 최소 파라미터만 설계하세요.
5. **로컬 토큰 모델** — 레지스트리 파일의 토큰은 동일 사용자의 다른 로컬 프로세스가 읽을 수 있습니다(데스크톱 MCP 생태계의 공통 가정). 다중 사용자·강화 환경에서는 토큰 순환을 앱 업데이트 주기와 맞추세요.

## 의도적으로 하지 않은 것

- 도구 입력의 엄격한 JSON Schema 검증 — 스펙도 오픈 이슈(#스키마 검증)이며, 최종 방어선은 도구 실행 코드 자체입니다. 서버는 required/type 위반 수준의 검증만 제공합니다(폴리필 경유 호출 시 페이지가 자체 검증).
- 프레임별 세밀한 권한 UI — 현재는 앱 단위 확인 훅만 제공. 도구별 영구 권한은 로드맵.
